# shmobj

Позволяет создавать сложные `dict`/`list` структуры в разделяемой памяти (и передавать информацию о них между
процессами).  
Структура создается одна общая для всего пула процессов.
Это сильно экономит память и снижает оверхед на операции сериализацию\десериализацию.

## Зачем это нужно

Основная проблема паралельного программирования на питон это GIL. Интерпретатор исполняет только один поток в один
момент времени.
Ради реальной конкурентности запускают несколько процессов. Но, процессы изолированы, они не разделяют память так, как
это делают потоки.
Каждый процесс — это отдельный экземпляр интерпретатора Python, он имеет свой собственный GIL и свою собственную копию
памяти.
Часто бывает разным процессам одного пула, нужны общие данные: справочник, настройки системы, общие метрики. Копии всего
этого живут в каждом процессе и объем свободной памяти падает вместе с ростом числа процессов.
К примеру: если запущено 8 воркеров и каждому из них нужен один и тот же набор данных (весом скажем 100 мегабайт), у
каждого воркера будет своя копия объектов, и восемь воркеров держат
восемь копий, всего 800 мегабайт.

### Прокси без полной копии

С `shmobj` все процессы читают одни и те же страницы общей памяти.
`shmobj` кладёт структуру в общую память один раз.
Процессы подключаются к ней по имени.
Читатель создает прокси с интерфейсом `Mapping` и `Sequence`, которые берут значения прямо из общего буфера.  
`FrozenDict` реализует `Mapping`, а `FrozenList` — `Sequence`.
Доступны привычные операции: `[]`, `get()`, `in`,`len()`, итерация и срезы списков.
Срез `FrozenList` также остаётся представлением без копирования.
Структура не распаковывается: Python-объекты создаются только для значений, к
которым процесс обратился, а подключение занимает микросекунды при любом объёме.

Для обмена ссылками на новые наборы данных можно использовать [Pub/Sub](#pubsub).

## Экономия памяти

Набор из миллиона записей вида `{"id", "name", "score", "tags": [...], "ok", "x"}` (эталон из
`doc/spec/07-testing.md` §5).
Каждый процесс загружает данные и один раз проходит по всем записям. Linux x86_64, Python 3.13, release-сборка.

| Процессов | Без `shmobj` (`pickle` в каждом) | С `shmobj` |
|----------:|---------------------------------:|-----------:|
|         1 |                           628 МБ |     168 МБ |
|         4 |                           2.5 ГБ |     168 МБ |
|         8 |                           5.0 ГБ |     168 МБ |

Подключение к сегменту — около 50 мкс, `pickle.loads` того же набора — 1.5 с.

### Компромисс: память вместо скорости доступа

Обращение по ключу или индексу в `shmobj` примерно в **3–6 раз медленнее**, чем в обычных `dict` и `list`. Для горячих
циклов используйте пакетные операции и итераторы:

- `get_many()` — получить несколько значений за одно обращение;
- `iter_values()` и `iter_items()` — перебирать значения и пары;
- `materialize()` — один раз скопировать нужную ветку в обычные `dict`/`list`, если с ней предстоит много работать.

`get_many()` позволяет получить несколько значений за один вызов. `materialize()` создаёт глубокую копию в обычные
Python-объекты.

Подробные
замеры: [doc/status.md](doc/status.md#базовые-замеры-release-linux-x86_64-python-313-эталонный-набор-spec07-testingmd-5).

## Быстрый старт

Процесс-владелец создаёт сегмент и передаёт его имя другим процессам любым удобным способом — например, через аргументы
запуска или переменную окружения:

```python
import shmobj

segment = shmobj.create({
    "users": [
        {"id": 1, "name": "Ann", "score": 42},
        {"id": 2, "name": "Bob", "score": 37},
    ]
})

print(segment.name)  # имя передать процессам-читателям
```

Читатель подключается к уже созданному сегменту:

```python
import shmobj

with shmobj.attach(segment_name) as segment:
    users = segment.root["users"]

    print(users[0].get_many(["id", "name"]))
    total = sum(user["score"] for user in users.iter_values())
```

### Pub/Sub

А если нужно редактировать данные?
Набор данных строго readable. Но можно подписаться на новые наборы.

`shmobj.channel` — Pub/Sub между двумя процессами (обертка над сокетами).
Publisher публикует набор данных целиком (снимок), subscriber держит ссылку на последний: `subscriber.latest` или колбэк
на каждый новый.
Каждый снимок — отдельный кусок общей памяти, по сокету идёт только ссылка на него (на Linux — дескриптор memfd, на
Windows — имя).
Старые снимки освобождаются, когда отпущены их прокси.

Publisher не ждёт subscriber: если тот отстал, `publish()` возвращает `False` и снимок пропускается. Поддерживается на
**Linux и Windows**. После завершения или падения любой из сторон ресурсы освобождает ОС.

```python
import sys
from shmobj import channel

WINDOWS = sys.platform == "win32"
# Процесс писатель
with tempfile.TemporaryDirectory() as tmp, channel.Publisher() as pub:
    address = pub.accept_in_thread(channel.listen(("127.0.0.1", 0) if WINDOWS else os.path.join(tmp, "snapshots.sock")))
    # Снимок собирается один раз (Linux — запечатанный memfd, Windows — SharedMemory) и уходит всем
    # подписчикам без ожидания. False — у кого-то полна очередь, ему этот снимок пропущен.
    # Ушедшие подписчики корректно закрываются сами.
    pub.publish({"tick": tick, "vms": {vm: {"cpu": tick % 100} for vm in range(100, 110)}})

# Процесс читатель 
with channel.Subscriber(channel.connect(address)) as sub:
    # wait() спит, пока не придёт снимок: True — sub.latest сменился на свежий (корень, FrozenDict поверх
    # общей памяти, без копирования); False — писатель закрыл канал.
    while sub.wait():
        print(f"читатель {os.getpid()}: new obj={sub.latest}\n")  
```

Или если читатель один:

```python
pub_sock, sub_sock = shmobj.channel.socketpair()

publisher = shmobj.channel.Publisher(pub_sock)
publisher.publish({"vms": {101: {"cpu": 0.5}}})

subscriber = shmobj.channel.Subscriber(sub_sock)
print(subscriber.latest)
```
Или так
```python
# планировщик
pub = channel.Publisher(name='vps-metrics')
pub.accept_in_thread(channel.listen('\0vps-metrics'))
pub.publish(snapshot)

# веб, когда нужно
sub = channel.Subscriber(channel.connect('\0vps-metrics'))
sub.receive()
print(ssub.latest)

```

## Есть же `multiprocessing.shared_memory`

SharedMemory - это посути массив байт, shmobj - оперирует удобными `dict`/`list` подобными объектами и питоновыми
литералами.
SharedMemoryManager использует `pickle` внутри себя, а это значит, полная копия экземпляра в каждом процессе и затраты
на сериализацию/десериализацию.

## Почему не хватает `fork`

Дочерний процесс после `fork` получает память родителя без копирования, пока страницы не меняются (copy-on-write). Для
Python-объектов это не работает:

- **Чтение — тоже запись.** Каждое обращение к объекту меняет его счётчик ссылок, а он лежит в заголовке объекта.
  Страница с объектом копируется в память ребёнка. Один проход по миллиону записей копирует около **340 МБ в каждый**
  дочерний процесс — даже после `gc.freeze()`, который убирает записи сборщика мусора.
- **Данные фиксируются в момент `fork`.** Обновление в родителе дети не увидят; новый набор — только перезапуском
  процессов.
- **Нужен общий родитель с уже загруженными данными.** Независимые процессы и сервисы так данные не разделят.
- **`fork` есть не везде.** На Windows его нет с Python 3.14 на Linux по умолчанию  `forkserver` — при них данные в
  каждом процессе загружаются заново.

Страницы сегмента `shmobj` никто не меняет: счётчики ссылок есть только у прокси и прочитанных значений, а не у данных
в общей памяти.

## Возможности

### Поддерживаемые данные

`dict`, `list`, `tuple`, `None`, `bool`, `int` любой длины, `float`, `str` и `bytes`. Ключи словарей должны быть
скалярными значениями.

Контейнеры доступны только для чтения. Для изменения данных нужно создать и опубликовать новый сегмент.

### Работа с буферами и файлами

`dumps` даёт тот же формат, что и сегмент, а `loads` открывает его поверх любого буфера: `bytes`, `mmap`,
`SharedMemory`. Именованный сегмент для этого не нужен:

- **Файл и `mmap`.** Набор собирается один раз и пишется в файл; процессы отображают файл в память и читают его
  страницы из кеша ОС — тоже одна копия на всех. Файл переживает перезапуск и перезагрузку, его можно выкладывать
  вместе с приложением. Подключение по-прежнему мгновенное: ОС подгружает с диска только прочитанные страницы.
- **Общий файловый дескриптор.** Буфер передаётся другому процессу дескриптором (memfd, файл, унаследованный при
  запуске), а не по имени; после закрытия всех дескрипторов ОС освобождает память сама. Так устроен Pub/Sub на Linux.
- **`bytes` из кеша или сети.** Большой блоб из Redis, с диска или по сокету читается выборочно: нужные поля без
  распаковки всего, как пришлось бы с `pickle` или JSON.

```python
import mmap
import shmobj

blob = shmobj.dumps(data)
root = shmobj.loads(blob)  # прокси поверх bytes

with open("data.bin", "wb") as file:  # один раз, при сборке набора
    file.write(blob)

with open("data.bin", "rb") as file:  # в каждом процессе
    mapped = mmap.mmap(file.fileno(), 0, access=mmap.ACCESS_READ)
    root = shmobj.loads(mapped)
```

`dumps_into(obj, alloc)` записывает данные непосредственно в предоставленный буфер без создания промежуточного объекта
`bytes`.

Подробнее: [Pub/Sub в doc/usage.md](doc/usage.md#канал-снимков-linux-windows).

### Проверка целостности и отладка

- `attach(name, verify=True)` проверяет контрольную сумму сегмента при подключении.
- `validate(buf)` проверяет весь буфер; повреждённые данные также обнаруживаются при обращении к ним через
  `FormatError`.
- PyCharm и VS Code показывают прокси как обычные контейнеры — плагин `pydevd` устанавливается вместе с пакетом.

## Установка

Требуется **CPython 3.11 или новее**. ABI3 позволяет использовать один wheel для разных версий CPython.

- Ядро на Rust, Python bindings через PyO3.
- CPython ≥ 3.11, ABI3.
- Версия 1 — только чтение: опубликованные данные нельзя изменить.

### Готовые wheels

CI собирает wheels для следующих платформ:

- Linux x86_64 и aarch64;
- Windows x64;
- macOS arm64.

Готовые файлы доступны в артефактах задачи `wheels` в GitHub Actions. Для установки скачанного wheel:

```bash
pip install ./shmobj-<version>-cp311-abi3-<platform>.whl
```

> `shmobj.channel` поддерживается на Linux и Windows. На macOS конструкторы канала и `socketpair()` возвращают
`NotImplementedError`.

### Сборка из исходников

Нужен Rust stable:

```bash
pip install git+https://github.com/Aleksandrln/shmobj
```

## Жизненный цикл сегмента

- `close()` закрывает сегмент в текущем процессе. Контекстный менеджер вызывает `close()` автоматически.
- `unlink()` удаляет именованный сегмент из ОС и обычно вызывается процессом-владельцем, когда данные больше не нужны. 
  Выход из `with` сам по себе не вызывает `unlink()`.
- Прокси удерживают ссылку на `Segment`: память не освобождается, пока существует хотя бы один прокси.
- После `close()` обращение через ранее созданные прокси вызывает `SegmentClosedError`.
- Процессы, уже подключившиеся к сегменту, могут продолжать читать его после `unlink()` до собственного `close()`.
- В Windows сегмент существует, пока открыт хотя бы один дескриптор; `unlink()` ничего не делает.

Полное описание API и особенностей владения буферами: [02-api.md](doc/spec/02-api.md).
