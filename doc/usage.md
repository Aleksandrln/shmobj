## Общий набор данных

`create(obj)` собирает дерево в новый сегмент общей памяти, `attach(name)` открывает его в другом процессе за
O(1): читается только заголовок. Имя `segment.name` передаётся читателям любым способом — аргументом задачи пула, через
`initializer` пула ([examples/shared_pool.py](../examples/shared_pool.py)), переменной окружения.

```python
import shmobj

segment = shmobj.create({"users": [{"id": 1, "name": "ann"}], "limits": {"rps": 100}})

# в другом процессе
with shmobj.attach(segment.name) as seg:
    cfg = seg.root                                # FrozenDict
    cfg["users"][0]["name"]                       # 'ann'
    cfg["limits"].get_many(["rps", "burst"], 0)   # [100, 0]
    cfg.materialize()                             # обычные dict/list
```

- `seg.root` — `FrozenDict`, `FrozenList` или скаляр. Прокси ведут себя как `Mapping`/`Sequence` только для
  чтения: `[]`, `get()`, `in`, `len()`, итерация, `keys()/values()/items()`, `==` с `dict`/`list`. Срез `FrozenList`
  — представление без копирования.
- Python-объекты создаются только для прочитанных значений. Каждое обращение к вложенному контейнеру создаёт новый
  прокси, кеша нет.
- `hash()` и `pickle` прокси — `TypeError`: в другой процесс передают имя сегмента или `materialize()`.

### Скорость доступа

Обращение по ключу или индексу в 3–6 раз медленнее, чем в `dict` и `list` (замеры — [status.md](status.md#замеры)).
В горячих циклах:

- `get_many(keys, default)` — несколько значений за один вызов;
- `iter_values()`, `iter_items()` — итераторы на Rust, быстрее `for k in d: d[k]`;
- `materialize()` — копия ветки в обычные `dict`/`list`, если с ней предстоит много работы.

## Файл, mmap и bytes

`dumps(obj)` даёт тот же формат, что и сегмент, `loads(buf)` открывает его поверх любого буфера без копирования:
`bytes`, `mmap`, `SharedMemory.buf`, memfd.

- **Файл и `mmap`.** Набор собирается один раз и пишется в файл; процессы отображают файл и читают страницы из кеша
  ОС — одна копия на всех. Файл переживает перезапуск, его можно выкладывать вместе с приложением; ОС подгружает с
  диска только прочитанные страницы ([examples/file_mmap.py](../examples/file_mmap.py)).
- **Общий дескриптор.** Буфер передаётся дескриптором (memfd, унаследованный файл), а не по имени; после закрытия
  всех дескрипторов ОС освобождает память сама. Так устроен канал на Linux.
- **`bytes` из кеша или сети.** Блоб из Redis, с диска или по сокету читается выборочно, без распаковки целиком.

`dumps_into(obj, alloc)` пишет сегмент в буфер `alloc(size)` (например, `mmap` файла нужного размера) без
промежуточных `bytes`.

`loads(buf)` удерживает экспорт буфера: пока живы прокси, `mmap.close()` у исходного объекта даёт `BufferError`.

## Проверка данных

- Без флагов `loads`/`attach` проверяют только заголовок, остальное — при каждом чтении: границы, типы узлов,
  порядок ссылок. Испорченный сегмент даёт `FormatError` при обращении к испорченному месту, без падения процесса.
- `verify=True` дополнительно сверяет контрольную сумму всего тела (O(n)). Ловит случайную порчу; от подделки не
  защищает — сумму можно пересчитать.
- `validate(buf)` — полный обход: сумма, все узлы, UTF-8, ключи, индексы KEYTABLE. После него `FormatError` при
  чтении невозможен.

## Жизненный цикл сегмента

- `close()` закрывает сегмент в текущем процессе; выход из `with` вызывает `close()`.
- `unlink()` удаляет имя сегмента из ОС; вызывает владелец, когда данные больше не нужны. Выход из `with` его не
  вызывает, кроме `create(..., unlink_on_close=True)`.
- Прокси держат ссылку на `Segment`: память не освобождается, пока жив хотя бы один прокси. После `close()`
  обращение через них — `SegmentClosedError`.
- Подключившиеся процессы читают сегмент и после `unlink()`, до своего `close()`.
- Windows: сегмент живёт, пока открыт хотя бы один handle; `unlink()` ничего не делает.
- Linux и macOS: сегмент — объект POSIX shared memory (на Linux — файл в `/dev/shm`, то есть в RAM). Он живёт до
  `unlink()`, а не до выхода создателя. Создатель вышел без `unlink()` — сегмент удаляет `resource_tracker` с
  предупреждением о leaked shared_memory. Убита вся группа процессов (остановка контейнера, systemd по cgroup, OOM) —
  сегмент остаётся до перезагрузки или `rm /dev/shm/<имя>`.
- `attach` не регистрирует сегмент в `resource_tracker` (3.13+ — `track=False`, 3.11–3.12 — снятие регистрации):
  выход читателя сегмент не удаляет.

## Обновление данных

Набор только для чтения: для изменения публикуют новый снимок целиком, читатели переключаются на него.

| | Канал `shmobj.channel` | Последний снимок `shmobj.latest` |
|---|---|---|
| ОС | Linux, Windows | Linux, Windows, macOS |
| Новый снимок | Уведомление: `wait()`, `await wait_async()`, колбэк `attach` | Опрос `get()` |
| Связь | Сокет: адрес, пара сокетов или унаследованный сокет | Имя |
| После падения | В ОС ничего не остаётся | Linux и macOS: имена в `/dev/shm` до следующего писателя |
| Неизменность снимка | Linux: memfd запечатан ядром | На писателе |

### Канал снимков

Один писатель (`Publisher`), сколько угодно читателей (`Subscriber`). Снимок собирается один раз на всех: на Linux —
запечатанный memfd, по сокету AF_UNIX идёт дескриптор; на Windows — именованная `SharedMemory`, по loopback TCP идёт
имя, читатель подтверждает приём. Новый подписчик сразу получает последний снимок. Старые снимки освобождаются,
когда отпущены их прокси.

**Писатель.**

- `publish(obj)` не блокирует. `False` — у кого-то из подписчиков полна очередь, ему этот снимок пропущен, остальные
  получают. Без подписчиков снимок только запоминается для следующего.
- Подписчики по адресу: `pub.accept_in_thread(channel.listen(address))` — фоновый поток,
  `pub.accept_in_loop(channel.listen(address))` — цикл asyncio. Уход подписчиков — не ошибка.
- Без приёма подключений (`Publisher(sock)`, `add`): последний подписчик закрыл канал — `BrokenPipeError`.
- `close()` (и выход из `with`) останавливает приём, закрывает сокеты и отпускает снимки писателя.

**Читатель.** `Subscriber` владеет сокетом; `latest` — корень последнего снимка (`None` до первого), переживает
закрытие канала. Новый снимок:

| Код | Как ждать |
|---|---|
| Без asyncio | `while sub.wait():` — сон в ядре до снимка; `False` — канал закрыт или истёк `timeout` |
| asyncio, цикл ожидания | `while await sub.wait_async():` — то же, не блокируя цикл |
| asyncio, в фоне | `sub.attach(callback)` — `callback(latest)` на каждый снимок; в запросе — `sub.latest` |
| Несколько сокетов в одном потоке | `sub.fileno()` в своём `selectors`, затем `sub.receive()` без ожидания |

В asyncio сокет читает приём в цикле: его включает `attach` или первый `wait_async`. Колбэк и `wait_async`
работают вместе, `wait_async` можно ждать в нескольких задачах — снимок будит всех. Синхронный `wait()` при этом —
`ValueError`, до `detach()`.

`Subscriber` не переподключается сам: после ухода писателя читатель подключается заново
([examples/channel_pubsub.py](../examples/channel_pubsub.py),
[examples/channel_pubsub_async.py](../examples/channel_pubsub_async.py)).

**Адрес.**

- Linux, абстрактный `"\0имя"` — имя сокета, а не файл. Ядро освобождает его с последним дескриптором, в том числе
  после `kill -9`, и перезапущенный писатель сразу занимает прежний адрес. Прав доступа у него нет: подключиться или
  занять имя первым может любой процесс. Виден только в своём сетевом namespace — из другого контейнера не найти.
- Linux, путь к файлу — права файловой системы; файл остаётся после выхода писателя, перед `listen` его удаляют.
- Windows — `("127.0.0.1", порт)`.
- `channel.connect(address, wait_writer=True)` ждёт, пока писатель не начнёт слушать (число — срок в секундах, затем
  `ConnectionRefusedError`); в asyncio — `await channel.connect_async(...)`. Ошибка в адресе тоже выглядит как
  ожидание, поэтому для отладки удобен срок.

**Без адреса.** Если читатель сам запускает писателя (или наоборот): `channel.socketpair()`, второй конец ребёнок
наследует через `spawn_kwargs(sock)` — `pass_fds` на Linux, `startupinfo` с `handle_list` на Windows
([examples/channel_spawn.py](../examples/channel_spawn.py)).

**Воркеры Gunicorn/Uvicorn.** Писатель — отдельный процесс: воркеры перезапускаются, а он должен жить дольше них.
Воркер подключается при старте (lifespan startup в Uvicorn, `post_worker_init` в Gunicorn) и вызывает
`sub.attach()`; в обработчике запроса — `sub.latest`. Прокси снимка нельзя держать в глобальных кешах: такая ссылка
не даёт освободить старые снимки.

**Очередь.** У каждого подписчика своя: на Linux — `SO_SNDBUF` (`Publisher(sndbuf=...)`), каждое непрочитанное
сообщение держит memfd; на Windows — 4 неподтверждённых снимка. Читатель берёт из очереди последний, прочие
закрывает. Одновременно живут последний снимок, снимки в очередях и у прокси читателей — не копия на каждого.

**Windows.** Печатей нет — снимок не меняет только сам писатель. Снимок, который писатель не успел отдать до
`close()` или выхода, теряется.

**macOS.** `channel.SUPPORTED` ложно, конструкторы и `socketpair()` дают `NotImplementedError`; используйте `latest`.

Протокол передачи — [api.md §6](api.md#6-канал-снимков-shmobjchannel-linux-windows).

### Последний снимок по имени

Писатель кладёт снимок под именем, читатель забирает последний, когда нужен. Процессы запускаются в любом порядке,
перезапуск писателя читателям не мешает ([examples/latest_pubsub.py](../examples/latest_pubsub.py)).

- Снимки — именованные сегменты `<name>.<gen>`, номер текущего — в управляющем сегменте `<name>`. О новом снимке
  читатель узнаёт опросом `get()`: проверка — чтение 40 байт; пока снимок тот же, `get()` возвращает тот же объект.
- `put()` удаляет прежний снимок; открытые у читателей отображения это не трогает.
- `writer.close()` и выход интерпретатора удаляют имена писателя; читатели дочитывают открытое.
- Linux и macOS: имя — объект POSIX shared memory, живёт до `shm_unlink`, поэтому читатель находит снимок без живого
  писателя. После падения писателя остаются `<name>` и последний снимок; следующий `Writer` с тем же именем
  подхватывает нумерацию и удаляет их. Windows: объект живёт, пока открыт handle, после падения ничего не остаётся.
- macOS: имя вместе с `.<gen>` — не длиннее 30 символов.

Устройство управляющего сегмента — [api.md §7](api.md#7-последний-снимок-по-имени-shmobjlatest).

## Отладчик

PyCharm и VS Code (debugpy) раскрывают `FrozenDict`, `FrozenList` и `keys()`/`values()`/`items()` как обычные
контейнеры: дети — по ключам и индексам, значение — начало содержимого. У прокси есть узел `methods` — сигнатура и
первая строка докстринга каждого публичного метода (pydevd методы не показывает). Это плагин pydevd из колеса
(`pydevd_plugins/extensions/pydevd_plugin_shmobj.py`): pydevd находит его сам, настраивать IDE не нужно. Плагин
загружается один раз за сеанс отладки — после установки колеса сеанс перезапустить.
