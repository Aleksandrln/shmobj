# 02. Python API

Контракт с типами: `python/shmobj/__init__.pyi`.

## 1. Модуль

```python
import shmobj

seg = shmobj.create(data)                 # новая SharedMemory, имя генерируется
seg.name                                  # передать в другие процессы

# другой процесс
with shmobj.attach(name) as seg:
    users = seg.root["users"]             # FrozenList
    names = users[0].get_many(["id", "name"])
    total = sum(u["score"] for u in users.iter_values())
```

| Функция | Описание |
|---|---|
| `dumps(obj, *, dedup=True, checksum=True) -> bytes` | Собрать сегмент в `bytes` |
| `dumps_into(obj, alloc, *, dedup=True, checksum=True) -> int` | Собрать сегмент и записать в начало буфера `alloc(size)` (записываемый, C-непрерывный, не короче `size`, иначе `ValueError`); возвращает `size`. Без промежуточных `bytes`; экспорт буфера отпускается до возврата. Ошибка сборки — до вызова `alloc` |
| `loads(buf, *, verify=False) -> Value` | Корень поверх буфера без копирования. `verify=True` дополнительно проверяет контрольную сумму, O(n) |
| `create(obj, name=None, *, dedup=True, checksum=True) -> Segment` | `dumps` и запись в новую `SharedMemory`. Процесс-создатель становится владельцем сегмента |
| `attach(name, *, verify=False) -> Segment` | Подключение к существующему сегменту |
| `validate(buf) -> None` | Полная проверка формата, иначе `FormatError` |

`Value = None | bool | int | float | str | bytes | FrozenList | FrozenDict`

Параметры сборки:
- `dedup` — дедупликация одинаковых скаляров. Таблицы ключей дедуплицируются всегда.
- `checksum` — записать в заголовок xxh3_64 тела сегмента.

## 2. `Segment`

| Член | Описание |
|---|---|
| `root: Value` | Корневое значение; при каждом обращении создаётся новый прокси |
| `name: str \| None` | Имя `SharedMemory`; `None` для `loads` поверх произвольного буфера |
| `size: int` | `data_size` из заголовка |
| `close()` | Помечает сегмент закрытым, освобождает буфер и закрывает `SharedMemory` в этом процессе. Идемпотентен |
| `unlink()` | Удаляет именованный сегмент из ОС (на Windows ничего не делает, см. ниже) |
| `closed: bool` | |
| `__enter__` / `__exit__` | `close()` на выходе; `unlink()` не вызывается |

Жизненный цикл:
- Прокси держат сильную ссылку на `Segment`, поэтому сегмент не освобождается, пока жив хотя бы один прокси.
- После `close()` любое обращение через старые прокси даёт `SegmentClosedError`.
- `unlink()` вызывает тот, кто решает, что данные больше не нужны: обычно создатель.
  Процессы, которые уже подключились, продолжают работать до своего `close()`.
- Windows: сегмент существует, пока открыт хотя бы один дескриптор; `unlink()` ничего не делает.
- 3.11–3.12: `attach` снимает регистрацию сегмента в `resource_tracker`,
  в 3.13+ используется `SharedMemory(track=False)`.
- `loads(buf)` удерживает экспорт буфера (`PyBuffer`). Пока живы прокси, `mmap.close()`
  или `SharedMemory.close()` у исходного объекта вызовут `BufferError`. Это штатное
  поведение buffer protocol.

## 3. `FrozenDict` — `collections.abc.Mapping`

| Метод | Семантика |
|---|---|
| `d[key]` | Значение или `KeyError`. Для нехэшируемого ключа — `TypeError`, как у `dict`. Для хэшируемого, но неподдерживаемого типа (например, `tuple`) — `KeyError` |
| `get(key, default=None)`, `key in d`, `len(d)` | Как у `dict` |
| `iter(d)`, `keys()`, `values()`, `items()` | Порядок вставки исходного `dict`. `keys()`/`values()`/`items()` возвращают представления (`KeysView`/`ValuesView`/`ItemsView`-совместимые) без копирования |
| `get_many(keys, default=<нет>) -> list` | Значения для итерируемого `keys` в его порядке. Без `default` первый отсутствующий ключ даёт `KeyError`; с `default` он подставляется |
| `iter_values() -> Iterator[Value]` | Итератор значений в порядке вставки |
| `iter_items() -> Iterator[tuple[Value, Value]]` | Итератор пар |
| `materialize() -> dict` | Глубокая копия в обычные объекты |
| `==` | Равен любому `Mapping` с теми же парами; порядок не важен, как у `dict` |
| `hash()` | `TypeError` (`__hash__ = None`) |
| `repr()` | `<FrozenDict len=N>`, без обхода данных |
| `pickle` | v1: `TypeError` с подсказкой использовать `materialize()` или передать имя сегмента |

## 4. `FrozenList` — `collections.abc.Sequence`

| Метод | Семантика |
|---|---|
| `l[i]` | Отрицательные индексы поддерживаются; `IndexError` |
| `l[a:b:c]` | `FrozenList`-представление без копирования |
| `len`, `iter`, `in`, `index`, `count`, `reversed` | Как у `list` (`index`/`count` по `==`) |
| `get_many(indices, default=<нет>) -> list` | Значения по индексам. Без `default` выход за границы даёт `IndexError` |
| `iter_values() -> Iterator[Value]` | То же, что `iter(l)`, явным методом для симметрии с `FrozenDict` |
| `materialize() -> list` | Глубокая копия; `tuple` из исходных данных возвращается как `list` |
| `==` | Равен `list` или `FrozenList` с равными элементами; `tuple` не равен (как у `list`) |
| `hash`, `repr`, `pickle` | Как у `FrozenDict` |

Типизированные списки (однородные `int`/`float`/`bool`, см. формат) возвращают
`int`/`float`/`bool`, и снаружи ничем не отличаются от обычных.

## 5. Исключения

| Исключение | База | Когда |
|---|---|---|
| `FormatError` | `ValueError` | Нарушение формата, неверный magic, версия или kind |
| `SegmentClosedError` | `ValueError` | Обращение к закрытому сегменту |
| `TypeError` | — | Неподдерживаемый тип при сборке; в сообщении путь, например `root['users'][3]['tags']` |
| `ValueError` | — | Цикл в данных или превышение лимитов |

## 6. Канал снимков `shmobj.channel` (Linux, Windows)

Один писатель отдаёт снимки целиком одному или нескольким читателям; читателю нужен только
последний. Снимок собирается один раз на всех подписчиков. Контракт с типами:
`python/shmobj/channel.pyi`.

```python
pub_sock, sub_sock = shmobj.channel.socketpair()     # pub_sock — в дочерний процесс: spawn_kwargs(pub_sock)
pub = shmobj.channel.Publisher(pub_sock)
pub.publish({"vms": {101: {"cpu": 0.5}}})            # True; False — очередь полна, снимок пропущен

sub = shmobj.channel.Subscriber(sub_sock)
sub.attach(lambda root: ...)                         # asyncio: колбэк на каждый новый снимок
sub.latest["vms"].get_many([101, 102], None)         # корень последнего снимка
```

Несколько читателей (воркеры Gunicorn/Uvicorn): писатель слушает `listen(address)` и подписывает
подключения — `pub.accept_in_thread(listener)` (поток), `pub.accept_in_loop(listener)` (asyncio) или
сам: `pub.add(conn)` на каждое принятое; читатель подключается `connect(address)`.

Передача на Linux:
- снимок собирается `dumps_into` прямо в memfd, затем memfd запечатывается `F_SEAL_SEAL | SHRINK | GROW | WRITE`;
- дескриптор идёт по сокету AF_UNIX SOCK_SEQPACKET (SCM_RIGHTS, `MSG_NOSIGNAL`), одно сообщение на
  снимок, тело — один байт; всем подписчикам — один и тот же memfd. Писатель держит дескриптор
  последнего снимка: его получает новый подписчик;
- читатель принимает только memfd с `F_SEAL_WRITE` и `F_SEAL_SHRINK` и отображает его на чтение.
  Без печатей снимок могли бы изменить или укоротить под читателем, и чтение отображения дало бы SIGBUS;
- имён в ОС нет: снимок освобождается, когда закрыт последний дескриптор и отпущен последний
  прокси.

Передача на Windows (нет memfd, печатей и передачи handle в сообщении):
- снимок — `create(obj, "<name>-<pid>-<номер>")`; по сокету (`socket.socketpair()`, loopback TCP)
  идёт имя строкой с `\n`;
- всем подписчикам — одно имя. Читатель разбирает очередь, открывает (`attach`) последний снимок,
  который ещё есть, и отвечает именами всех принятых строками с `\n`. Писатель читает
  подтверждения при следующем `publish` и закрывает снимок, когда тот не последний и подтверждён
  всеми, кому отправлен: до подтверждения снимок держит только он, и без этого снимок исчезал бы
  до открытия;
- объект ядра живёт, пока открыт хоть один handle: после падения любой из сторон ничего не
  остаётся, `unlink` не нужен. Снимок, который писатель закрыл до открытия (вышел), читатель
  пропускает;
- неизменность снимка держится на писателе: печатей нет, читатель открывает снимок на запись
  (`SharedMemory`). Чужие подтверждения (прежний писатель того же сокета) писатель пропускает.

После падения любой из сторон в ОС ничего не остаётся.

| Член | Описание |
|---|---|
| `SUPPORTED: bool` | Linux (`sys.platform`; CPython с `os.memfd_create`) или Windows. Иначе (macOS) конструкторы, `socketpair()` и `spawn_kwargs()` дают `NotImplementedError` |
| `socketpair()` | Linux — AF_UNIX SOCK_SEQPACKET, Windows — loopback TCP; концы равноправны, не наследуются |
| `listen(address, backlog=16)` | Слушающий сокет писателя. Linux — AF_UNIX SOCK_SEQPACKET, `address` — путь (файл не должен существовать) или абстрактное имя `"\0…"`; Windows — TCP, `address = (host, port)` |
| `connect(address)` | Сокет читателя, подключённый к `listen(address)` |
| `spawn_kwargs(sock) -> dict` | Аргументы `Popen`/`create_subprocess_exec` для наследования `sock`: `pass_fds` (Linux), `startupinfo` с `handle_list` (Windows; `sock` становится наследуемым). В дочернем процессе — `socket.socket(fileno=…)` с номером из родителя |
| `Publisher(sock=None, *, sndbuf=16384, name="shmobj")` | `sock` — первый подписчик (`add`). Linux: `SO_SNDBUF = sndbuf` у сокета каждого подписчика, `name` — имя memfd (видно в `/proc/<pid>/maps`). Windows: `sndbuf` не используется, `name` — префикс имён снимков |
| `Publisher.add(sock)` | Владеет `sock`, переводит в неблокирующий режим; последний снимок уходит сразу. Писатель закрыт — `ValueError` |
| `Publisher.accept_in_thread(listener) -> address` | `listener.getsockname()` — адрес для `connect`. Фоновый поток (daemon) ждёт `listener` в `selectors` и подписывает все ожидающие подключения. `add`, `publish`, `close` — под замком. Владеет `listener`: `close()` будит поток (своя пара сокетов), дожидается его и закрывает `listener` |
| `Publisher.accept_in_loop(listener, *, loop=None) -> address` | То же в цикле asyncio без потока: `loop.add_reader`, в цикле без него (ProactorEventLoop) — задача с `loop.sock_accept`. `close()` снимает приём с цикла и закрывает `listener` |
| `Publisher.subscribers -> int` | Число подписчиков; закрывшие канал убираются (и их сокеты закрываются) при `publish` |
| `Publisher.publish(obj, *, dedup=True, checksum=True) -> bool` | Одна сборка, отправка всем, не блокирует. `False` — у кого-то очередь полна, ему снимок пропущен. Снимок становится последним и без подписчиков. Последний подписчик закрыл канал — `BrokenPipeError` (следующий `publish` без подписчиков — без ошибки). Писатель закрыт — `ValueError` |
| `Publisher.close()` | Останавливает приём подключений, закрывает сокеты подписчиков и `listener`, отпускает снимки писателя. Windows: и неподтверждённые — читатели их не получат |
| `Subscriber(sock, *, verify=False)` | Владеет `sock`. `verify` передаётся в `loads`/`attach` для каждого снимка |
| `Subscriber.latest` | Корень последнего принятого снимка, `None` — снимков не было. Переживает закрытие канала |
| `Subscriber.receive() -> bool` | Разбирает очередь без ожидания и берёт последний снимок, прочие закрывает (Windows — подтверждает). `True` — `latest` сменился. Конец канала закрывает сокет. Linux: незапечатанный снимок — `ValueError`, `latest` прежний |
| `Subscriber.wait(timeout=None) -> bool` | Блокирующее ожидание для кода без asyncio: `receive()`, пока `latest` не сменится, между попытками — сон в своём `selectors` на сокете. `True` — новый снимок; `False` — истёк `timeout` или канал закрыт. После `attach` — `ValueError` |
| `Subscriber.attach(callback=None, *, loop=None)` | По умолчанию текущий цикл. `loop.add_reader`, а в цикле без него (ProactorEventLoop, Windows) — задача, которая ждёт `sock_recv(sock, 0)` (IOCP завершает его, когда есть данные или конец). `receive()` по готовности сокета, `callback(latest)` на каждый новый снимок. Исключения уходят в обработчик исключений цикла, приём продолжается. Конец канала снимает сокет с цикла |
| `Subscriber.detach()` | Снять с цикла, сокет открыт |
| `closed`, `close()`, `__enter__`/`__exit__` | У обоих концов; `close()` идемпотентен. `fileno()` — у `Subscriber`: ждать несколько сокетов в своём `select`/`selectors`, затем `receive()` |

Очередь у каждого подписчика своя и ограничена: на Linux — `sndbuf` (каждое непрочитанное
сообщение держит свой memfd), на Windows — 4 неподтверждённых снимка. Писатель не копит снимки, а
пропускает их отставшему; остальные получают. Одновременно живут последний снимок и снимки в
очередях и у прокси читателей, а не копия на каждого подписчика. Прежний снимок
освобождается, когда отпущены его прокси. На Linux отображение держит копию дескриптора (`mmap`),
так что живой снимок — это одно отображение и один дескриптор.

## 7. Последний снимок по имени `shmobj.latest`

Писатель кладёт снимок целиком, читатели забирают последний, когда нужно. Сокетов нет: читатели
подключаются по имени в любом порядке, писателя может ещё не быть, его перезапуск читателям не
мешает. Любая ОС с `SharedMemory`, включая macOS. Контракт с типами: `python/shmobj/latest.pyi`.

```python
w = shmobj.latest.Writer("metrics")
w.put({"vms": {101: {"cpu": 0.5}}})

r = shmobj.latest.Reader("metrics")         # другой процесс
r.get()["vms"].get_many([101, 102], None)   # корень последнего снимка; None — снимков не было
```

Устройство:
- снимок — именованный сегмент `<name>.<gen>` (`gen` в hex), собирается `create` прямо в
  SharedMemory; управляющий сегмент `<name>` (64 байта, LE): `magic = b"SHMOLAT1"`, `epoch` (u64,
  случайный при создании управляющего сегмента), `gen` (u64, номер текущего снимка, 0 — снимков
  нет), `state` (u64: 1 — писатель открыт, 2 — закрыт), `check = epoch ^ gen ^ (state << 56) ^
  0x53484D4F4C415431`. Несовпадение `magic` или `check` — сегмент пустой или прочитан посреди
  записи: читатель перечитывает;
- `put`: новый снимок, запись `gen` в управляющий сегмент, удаление прежнего снимка (POSIX —
  `shm_unlink`, Windows — закрытие handle). Открытые отображения удаление не трогает;
- `get`: (`epoch`, `gen`) те же — прежний корень (тот же объект); иначе `attach`. Снимка уже нет —
  писатель ушёл дальше, номер перечитывается (до 8 попыток, затем прежний корень). Windows: снимок,
  исчезнувший между двумя шагами открытия `SharedMemory`, даёт пустое отображение — `FormatError`
  при неизменном номере пробрасывается, при сменившемся — повтор;
- `state = 2`: читатель закрывает управляющий сегмент и открывает его по имени заново — на POSIX
  новый писатель создаёт новый, а прежнее отображение указывало бы на удалённый. `epoch` отличает
  новый управляющий сегмент с нумерацией с начала от прежнего.

Имена и их уборка:
- имена не регистрируются в `resource_tracker`: его уборка при выходе писателя оставила бы
  читателей на удалённом управляющем сегменте;
- `Writer.close()` (и выход интерпретатора, `weakref.finalize`) ставит `state = 2` и удаляет
  управляющий сегмент и последний снимок;
- после падения писателя на POSIX остаются управляющий сегмент и последний снимок; читатели получают
  этот снимок. Следующий `Writer` с тем же именем открывает управляющий сегмент, продолжает `gen` и
  `epoch` и удаляет оставшийся снимок при первом `put`. Имя снимка занято (осталось после падения
  между сборкой и записью номера; на Windows его держит читатель) — берётся следующий номер, на
  POSIX занятое удаляется;
- Windows: объект живёт, пока открыт хоть один handle; после падения ничего не остаётся.

| Член | Описание |
|---|---|
| `Writer(name)` | Открывает или создаёт управляющий сегмент. Один писатель на имя. Имя занято сегментом другого формата — `ValueError`. macOS: имя SharedMemory ≤ 30 символов, вместе с `.<gen>` |
| `Writer.put(obj, *, dedup=True, checksum=True)` | Новый снимок становится последним, прежний удаляется. Закрыт — `ValueError` |
| `Writer.close()` | `state = 2`, удаление своих имён. Идемпотентен |
| `Reader(name, *, verify=False)` | Ничего не открывает; `verify` — в `attach` каждого снимка |
| `Reader.get() -> Value \| None` | Корень последнего снимка; тот же объект, пока снимок не сменился. Управляющего сегмента нет — последний принятый корень (`None` до первого) |
| `Reader.close()` | Закрывает управляющий сегмент; последний корень остаётся, `get()` больше не обновляет. Идемпотентен |
| `name`, `closed`, `__enter__`/`__exit__` | У обоих |

Отличия от канала (§6): нет уведомления о новом снимке (читатель опрашивает `get()`), нет печатей
(неизменность снимка — на писателе), после падения писателя на POSIX остаются имена.

## 8. Зарезервированные имена (RW, не реализуются в v1)

`SharedDict`, `SharedList`, `create_rw`, `attach_rw`, `freeze`, `thaw`, модуль `shmobj.abc`.
