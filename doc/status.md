# Состояние

Версия 0.1.3, формат RO v1. Изменяемых структур (RW) нет — задел в [rw.md](rw.md).

## Есть

| Часть | Что |
|---|---|
| Формат и ядро | Заголовок, слоты, скаляры, LIST со всеми подтипами, DICT/KEYTABLE (LINEAR, SORTED32), `validate`. Сборка даёт те же байты, что эталон |
| Python API | `create`/`attach`/`close`/`unlink`, `unlink_on_close`, `dumps`/`dumps_into`/`loads`/`validate`, `FrozenDict`, `FrozenList` (срезы, `keys/values/items`, `get_many`, `iter_*`, `materialize`, `==`, `repr`, отказ `hash`/`pickle`), пути в ошибках сборки, циклы |
| Жизненный цикл | `resource_tracker` 3.11–3.12, `track=False` 3.13+ |
| Канал `shmobj.channel` | Linux — memfd, Windows — именованные снимки с подтверждением; несколько подписчиков, `listen`/`connect`/`connect_async` с ожиданием писателя, приём подключений в потоке и в asyncio, `wait`/`wait_async`/`attach`. macOS — `SUPPORTED = False` |
| `shmobj.latest` | `Writer.put`/`Reader.get` по имени, любая ОС; уборка имён в `close()` и при выходе, подхват после падения писателя |
| Отладчик | Плагин pydevd в колесе |

В рабочем проекте — Linux (Python 3.11–3.13) и Windows x86_64. macOS — только тесты CI на arm64;
в README поддержка macOS — частичная.

## Нет

- fuzz-целей (`validate`, случайный доступ); proptest круговой сборки в ядре.
- Тестов утечек (10⁶ операций: `sys.getrefcount` сегмента, `len(gc.get_objects())`, RSS), бенчмарков
  (`benches/`, `tests/bench_*.py`), полного перебора повреждений golden (≥ 10⁵ вариантов).
- Целей по скорости (таблица ниже).

## Тесты

- Ядро (`crates/shmobj-core/tests/core.rs`): golden, все однобайтовые изменения `records.bin` без паник.
- Эталон: `golden/*.bin` проходят `validate`, читаются в `golden/cases.py`, `dumps` даёт побайтово те же файлы;
  hypothesis — `dumps(v) == ref.build(v)`, взаимное чтение; вердикт `validate` на повреждённых сегментах совпадает с
  эталоном (5000 вариантов).
- API (`tests/test_api.py`), жизненный цикл (`test_lifecycle.py`): межпроцессное чтение через `spawn` и `fork`, без
  предупреждений `resource_tracker`.
- Канал (`test_channel.py`): последний из очереди, освобождение снимков (`/proc/self/maps`, `/proc/self/fd`), печати,
  пропуск при полной очереди, конец канала с обеих сторон, asyncio, несколько подписчиков, ожидание писателя.
  Протокол Windows гоняется и на Linux поверх `/dev/shm`.
- `latest` (`test_latest.py`): перезапуск и падение писателя (`kill -9`), занятые имена, читатель в другом процессе.
- Примеры (`test_examples.py`): все скрипты `examples/`; читатели по адресу переживают падение писателя.
- Отладчик (`test_debugger.py`, нужен `pydevd-pycharm`).

Обязательные граничные случаи для новых тестов: пустые контейнеры на всех уровнях и как корень; `int` 2⁵⁹−1, −2⁵⁹,
2⁵⁹, ±(2⁶³−1), −2⁶³, 2⁶⁴, ±2²⁰⁰; `float` −0.0, ±inf, NaN-значение, субнормальные; `str` 7 и 8 байт UTF-8,
многобайтный символ на границе 7 байт, `\0` внутри и в конце; словарь на 8 и 9 ключей; списки на границах ширин
(255/256, −128/−129, 2³²−1/2³², `[True, 1]`).

## Решения

- Дедупликация KEYTABLE, как в эталоне, считает `0.0` и `-0.0` одним ключом.
- Вложенность при сборке и `materialize` ограничена `MAX_DEPTH = 1000` (`ValueError`); `validate` итеративный и
  глубину не ограничивает.
- `keys()/values()/items()` возвращают `collections.abc.KeysView/ValuesView/ItemsView` поверх прокси.
- Строки — `PyString::from_bytes` (`PyUnicode_FromStringAndSize`, ASCII CPython распознаёт сам); `char_count` не
  используется и не проверяется `validate`. Свой ASCII-путь через `PyUnicode_New` и `memcpy` под abi3 невозможен:
  `PyUnicode_New` нет в стабильном ABI.
- `zerocopy` не используется: заголовок разбирается через `from_le_bytes`.
- Канал на Python, не в Rust: только системные вызовы и asyncio, а `shmobj-core` без `unsafe`. Пакет
  `channel/`: asyncio — только в `_aio.py`, его импортируют asyncio-методы, так что синхронный код `asyncio` не
  загружает (около 20 мс на запуск процесса); протокол другой платформы тоже не загружается. Константы печатей
  заданы числами (`linux/fcntl.h`): в `fcntl` их может не быть.
- Канал на Windows — по имени, а не `DuplicateHandle`: объект ядра живёт, пока открыт handle, имя после падения не
  остаётся, а `attach` уже есть. Подтверждение нужно, потому что без handle писателя снимок исчезает до открытия
  читателем. `SharedMemory` на Windows открывает имя в два шага (`OpenFileMapping`, затем `mmap` с `tagname`);
  исчезни снимок между ними — `mmap` создаст пустой, и `attach` даст `FormatError`.
- Читатель канала в asyncio: сокет читает один приём в цикле (`_aio.LoopReceiver`, живёт от `attach` или первого
  `wait_async` до `detach`), `wait_async` ждёт его уведомления (`_Broadcast`: будит всех, счётчик против своего
  `seen`). Так работают вместе колбэк и `wait_async`, несколько `wait_async` сразу, и снимки между вызовами не
  теряются. Ошибку приёма получают ждущие `wait_async` (с трейсбеком приёма); без них при колбэке — обработчик
  исключений цикла (приём живёт сам по себе), без колбэка — следующий `wait_async`. Не забранная до снятия
  приёма — тоже обработчик цикла.
  Синхронный `wait()` при приёме в цикле — `ValueError`: он ждёт из другого потока, совмещение потребовало бы
  межпоточной синхронизации.
- `shmobj.latest` — на именах, а не на сокетах: читатель подключается сам, в любой момент, и работает на macOS. Цена —
  имена на POSIX после падения писателя и опрос вместо уведомления. Имена не регистрируются в `resource_tracker`
  (`_shm.open_shm(track=False)`): уборка трекера при выходе писателя удалила бы управляющий сегмент из-под читателей.
  Читатель открывает управляющий сегмент не через SharedMemory (`_shm.open_existing`): между `shm_open` и
  `ftruncate` писателя сегмент имеет длину 0, его mmap — ошибка, и SharedMemory при OSError (macOS) удаляет имя.
- Внутренняя `shmobj._core.open_segment(buf, *, name, on_close, on_unlink, verify)` создаёт `Segment`;
  `create`/`attach` в `python/shmobj/_shm.py` передают в неё колбэки `SharedMemory`.

## Замеры

Release, Linux x86_64, Python 3.13. Набор — 10 000 записей
`{f"user{i}": {"id": i, "name": f"name{i}", "score": i * 1.5, "tags": ["a", "bb", i], "ok": True, "x": None}}`;
множитель — относительно той же операции на `dict`/`list` в том же цикле.

| Метрика | Сейчас | Цель |
|---|---|---|
| Размер / Python-объекты (`tracemalloc` на `deepcopy`) | 41% (1.57 МБ, как у эталона) | ≤ 45% |
| `fd[k]`, словарь ≤ 8 ключей | 4.7× `dict` | ≤ 3× |
| `fd[k]`, 10 000 ключей | 6.3× | ≤ 3× |
| `fl[i]` | 3.2× `list` | ≤ 3× |
| `get_many`, 1000 ключей, на ключ | 9.0× | ≤ 2× |
| `iter_values`, на элемент | 12.8× | ≤ 2.5× |
| `dumps` | 4.0× `pickle.dumps` | ≤ 3× |
| `materialize()` | — | ≤ 2× `pickle.loads` |
| `attach(name)` | ~50 мкс | ≤ 50 мкс, не зависит от размера |
| Прирост RSS читателя после `attach` и `root["user42"]["name"]`, сегмент 100 МБ | — | ≤ 1 МБ |

## Будущие оптимизации

Догадки о том, куда уходит время; порядок — по профилю. Цели — таблица «Замеры».

- Прокси хранит разобранный заголовок узла (подтип, длину, начало элементов) и не разбирает его заново на каждом
  доступе; остаётся только проверка `closed`.
- `get_many` без промежуточных прокси на каждый ключ.
- `get_many` с быстрым путём для `list`/`tuple`: индексация готовой последовательности вместо обхода итератором.
- Итераторы `iter_values`/`iter_items` берут сегмент (`with_seg`) один раз, а не на каждом шаге.
- Дедупликация при сборке без аллокаций на каждый скаляр.

Почти ничего не дадут: интерполяционный поиск в SORTED32 (двоичный поиск по 10 000 ключей — около 14 сравнений `u64`,
вызов из Python дороже на порядок) и свой ASCII-путь для `str` (см. «Решения»).
